# 08. 2단계 운영: 이슈 분해, 작업 순서, 조별 협업 오케스트레이션

## 이 장의 목표

- 구현 전에 작업을 어떻게 나누어야 conflict와 리뷰 비용을 줄일 수 있는지 이해한다.
- GitLab issue, branch, MR을 하나의 운영 흐름으로 연결한다.
- 3인 1조 실습에서 누가 언제 개입해야 하는지 구체화한다.
- merge 순서와 책임을 미리 설계하는 습관을 만든다.

## 선행 개념

- feature branch, MR, 리뷰, 승인 흐름을 이해했다.
- conflict가 어떤 상황에서 생기는지 경험했다.

## 왜 협업은 구현보다 먼저 설계해야 하나?

초보 팀은 종종 "일단 각자 구현하고 나중에 합치자"라고 생각한다. 이 방식은 거의 반드시 아래 문제를 만든다.

- 작업 범위 중복
- 같은 파일 동시 수정
- 리뷰 포인트 불분명
- merge 순서 충돌
- 책임 소재 불명확

즉, conflict는 코드에서만 생기는 것이 아니라 운영 설계 부재에서도 생긴다.

## 실습 시나리오

팀은 다음 스프린트에서 아래 3가지 개선을 하기로 했다.

- 간식 추천 이유 문구 개선
- 버튼 스타일과 카드 여백 개선
- README 실행 가이드 보강

이제 이 작업을 issue, branch, MR 단위로 나눠 본다.

## 실습 1. 작업을 이슈로 분해하기

권장 예시:

| 이슈 | 작업 내용 | 담당 |
| --- | --- | --- |
| `#11` | 추천 이유 문구 개선 | 개발자 A |
| `#12` | 버튼/카드 스타일 개선 | 개발자 B |
| `#13` | README 실행 가이드 보강 | 리뷰어 또는 개발자 A |

### 이슈를 나누는 기준

- 결과가 하나의 문장으로 설명 가능한가?
- 리뷰 범위가 과하게 크지 않은가?
- 서로 다른 사람이 병렬 작업해도 되는가?

## 실습 2. 브랜치 이름과 이슈 연결

브랜치 예시:

- `feature/snack-copy-11`
- `feature/snack-style-12`
- `docs/readme-guide-13`

이슈 번호를 브랜치에 넣는 이유:

- 추적이 쉽다.
- 브랜치 목적이 명확하다.
- MR과 이슈 연결이 빨라진다.

## 실습 3. MR 설명에 이슈 연결

MR 본문에 아래처럼 적는다.

```md
## 관련 이슈

- Closes #11
```

### 왜 중요한가?

- merge 시 이슈 상태와 코드 반영이 연결된다.
- 나중에 "이 작업이 왜 시작되었는가?"를 추적하기 쉽다.

## 실습 4. merge 순서 설계

협업에서 같은 시점에 모두 merge하면 안전할 것 같지만 실제로는 순서가 중요하다.

예시:

1. README 보강
2. 추천 문구 개선
3. 스타일 개선

### 왜 이런 순서를 잡을 수 있나?

- README는 코드 충돌 가능성이 낮다.
- 문구 개선과 스타일 개선은 UI 확인이 필요하다.
- 문구와 스타일이 같은 화면을 바꾸므로 merge 간격이 길어지면 conflict 가능성이 올라간다.

## 역할별 운영 책임

### 개발자

- 이슈를 하나의 설명 가능한 변경으로 구현
- 브랜치 생성과 MR 생성
- 리뷰 피드백 반영

### 리뷰어

- 코드를 보기 전에 요구사항과 확인 방법부터 점검
- 병렬 작업 간 충돌 가능성 조기 경고
- merge 순서가 적절한지 검토

### 승인자 또는 Maintainer

- 보호 브랜치 정책에 맞는 반영 순서 결정
- 충돌 가능성이 큰 작업의 우선순위 조정
- 필요한 경우 한 MR을 먼저 merge하고 다른 MR은 rebase 또는 merge 업데이트 지시

## 짧은 협업 미팅에서 확인할 질문

- 이 작업은 누구 책임인가?
- 어느 파일을 주로 건드리는가?
- 어떤 순서로 merge해야 안전한가?
- 리뷰어는 무엇을 특히 봐야 하는가?
- 충돌이 예상되면 사전에 어떻게 피할 것인가?

## 교육용 운영 보드 예시

```text
Backlog
- #11 추천 이유 문구 개선
- #12 버튼/카드 스타일 개선
- #13 README 실행 가이드 보강

In Progress
- feature/snack-copy-11
- feature/snack-style-12

Review
- docs/readme-guide-13

Done
- 이전 스프린트 완료 항목
```

## 충돌을 줄이기 위한 운영 규칙

- 한 MR은 한 목적만 담는다.
- 같은 파일을 여러 명이 건드릴 가능성이 크면 사전에 나눈다.
- merge 순서를 미리 정한다.
- 리뷰가 길어지면 최신 `main` 반영 계획도 같이 잡는다.
- "누가 merge하나"를 미리 정한다.

## 이 장의 핵심 문장

- 협업은 구현보다 먼저 설계된다.
- 승인자는 마지막에만 등장하는 사람이 아니다.
- 리뷰어도 코드를 보기 전에 범위와 운영 위험을 먼저 봐야 한다.

## 결과 확인 체크리스트

- 작업을 issue 단위로 나눴다.
- branch 이름에 작업 목적 또는 이슈 번호를 반영했다.
- MR 본문에 관련 이슈를 연결했다.
- 팀이 merge 순서를 미리 정했다.
- 역할별 책임 문장을 합의했다.
